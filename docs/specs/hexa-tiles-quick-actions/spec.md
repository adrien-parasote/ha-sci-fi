# Hexa Tiles Quick Actions — Implementation Spec

Document Type: implementation

## Overview

Les tuiles personnalisées de `custom:sci-fi-hexa-tiles` deviennent des boutons d'action rapide pour un téléphone utilisé comme télécommande (portail, lumière de la chambre, borne de recharge ; plus tard la télé, en simple allumer / éteindre — le radiateur est retiré, réponse au spike du 2026-11-18). Aucune nouvelle carte (décision utilisateur, [frame contract](../../frame-contracts/hexa-tiles-quick-actions.yaml)). Trois clés de tuile s'ajoutent — `states` (couleur, icône, libellé par état), `subtitle` (seconde ligne), `pending_timeout` — et trois clés déjà déclarées mais jamais lues sont branchées : `state_error`, `hold_action`, `double_tap_action` (constat F12 du [ledger](../../research/hexa-tiles-quick-actions/ledger.md), SHOW — `grep -n "state_error\|hold_action\|double_tap_action" src/cards/hexa-tiles/sci-fi-hexa-tiles.ts` → aucune ligne, lu le 2026-11-18). Un toucher exécute `tap_action` immédiatement, **sans aucune étape de confirmation** (veto utilisateur du 2026-11-18). Le retour « en cours » est porté par la carte : les covers template `cover.portail` / `cover.porte_garage` ne passent jamais par `opening` / `closing` (F5). Une config sans aucune des nouvelles clés se rend et se comporte exactement comme aujourd'hui.

Le toggle lui-même n'est pas codé ici : la carte émet `hass-action` avec `tap_action: {action: toggle}` et le frontend HA appelle le bon service par domaine (`open_cover` / `close_cover`, `turn_on` / `turn_off`…), F6 du ledger. La spec de la carte, [hexa-tiles.md](../cards/hexa-tiles.md), est amendée par ce lot (FR-14).

Vocabulaire : une **tuile personnalisée** est toute entrée de `tiles` (standalone ou agrégée `entity_kind`), par opposition à la tuile météo (agent's call : c'est le périmètre où la carte reçoit déjà ses `click`). Un **geste** est un toucher (FR-6), un appui long (FR-8) ou un double toucher (FR-9) ; un **geste toggle** est un geste dont l'action résolue a `action === 'toggle'` (pour l'appui long sans `hold_action`, l'action résolue est `more-info`, jamais `toggle`).

### Config cible (production, exemple validé au frame)

Exemple de config, illustration :

```yaml
type: custom:sci-fi-hexa-tiles
tiles:
  - standalone: true
    entity: cover.portail
    name: Portail
    tap_action: { action: toggle }
    states:
      closed: { color: "var(--sf-accent-on)", icon: mdi:gate, label: Fermé }
      open:   { color: "var(--sf-error)", icon: mdi:gate-open, label: Ouvert }
  - standalone: true
    entity: light.zbmini_l_dressing_parent
    name: Lumière
    subtitle: Chambre parents
    tap_action: { action: toggle }
    states:
      "on":  { color: "var(--sf-warning)", icon: mdi:lightbulb-on }
      "off": { icon: mdi:lightbulb-outline }
  - standalone: true
    entity: switch.mureva_evlink
    name: Charge
    subtitle: Voiture
    tap_action: { action: toggle }
    states:
      "on":  { color: "var(--sf-accent-on)", icon: mdi:ev-station, label: En charge }
      "off": { icon: mdi:ev-plug-type2, label: Charge terminée }
```

## Requirements

- **FR-1**: `SciFiHexaTileConfig` (`src/cards/hexa-tiles/config.ts`) gagne trois champs optionnels et un type exporté, déclarés comme ci-dessous ; aucun champ existant n'est renommé ni retiré (ADR-005), et `ActionConfig` (`src/types/config.ts`) n'est pas modifié — la carte transmet l'objet d'action tel quel, clés inconnues comprises (`perform_action`, `data`, `target`…).

```typescript
export interface SciFiHexaTileStateStyle {
  readonly color?: string;   // valeur CSS de couleur : '#00ff9d', 'red', 'var(--sf-accent-on)'
  readonly icon?: string;    // 'mdi:gate-open'
  readonly label?: string;   // seconde ligne quand cet état est courant
}

export interface SciFiHexaTileConfig {
  // … champs existants inchangés …
  readonly states?: Readonly<Record<string, SciFiHexaTileStateStyle>>;
  readonly subtitle?: string;
  readonly pending_timeout?: number;   // secondes
}
```

- **FR-2**: **Non-régression.** Une tuile sans `states`, `subtitle`, `pending_timeout`, `hold_action`, `double_tap_action` ni `state_error`, dont l'entité est présente, disponible et dans un état autre que `opening` / `closing`, produit le même `innerHTML` normalisé de `.hexa-tile` qu'avant ce lot (normalisé = marqueurs de commentaire Lit `<!--…-->` retirés et blancs consécutifs réduits à un espace ; les tuiles portent déjà `role="button"`, `tabindex="0"` et `aria-label="<nom>"` avant ce lot, `sci-fi-hexa-tiles.ts:436-438` — agent's call pour la règle de normalisation), et un toucher garde la précédence d'aujourd'hui : `tap_action` → `fireHassAction(this, tile, 'tap')`, sinon `link` → navigation, sinon `entity` → more-info, sinon rien [AE-5]. La tuile météo et l'en-tête ne changent pas.
- **FR-3**: **Style par état.** Pour une tuile standalone avec `entity`, si `tile.states` contient une clé **strictement égale** à `hass.states[entity].state` (casse comprise) et que la tuile n'est pas en erreur (FR-5) : si l'entrée a `color`, l'élément `.hexa-tile` porte `data-state-color="true"` et la propriété inline `--sf-tile-state-color: <color>` (posée par la CSSOM, `style.setProperty`, depuis une directive `ref` — jamais par concaténation dans l'attribut `style` ; `styleMap` est écarté au BUILD : son premier rendu concatène les déclarations en chaîne, `render()` de `lit-html/directives/style-map.js` 3.x, ce que TC-HQA-U-02 refuse) ; l'icône est `entry.icon` si présent, sinon l'icône calculée comme aujourd'hui (`active_icon` / `inactive_icon` / attribut `icon` / icône de domaine). Sans clé correspondante (ex. `opening`), la tuile se rend comme aujourd'hui. Les tuiles agrégées (`entity_kind`) ignorent `states`.
  - **FR-3.1**: **Config mal formée.** `tile.states` n'est lu que s'il est un objet simple (non `null`, pas un tableau, pas une chaîne) ; sinon il est traité comme absent. Une entrée n'est lue que si elle est un objet simple ; sinon elle est traitée comme absente. Les champs `color`, `icon`, `label` ne sont lus que s'ils sont des chaînes non vides ; sinon ils sont traités comme absents. Aucune de ces formes ne lève d'exception au rendu, et les autres tuiles se rendent normalement.
- **FR-4**: **Seconde ligne.** La seconde ligne est, dans l'ordre : `msg('Unavailable')` si l'entité est absente ou `unavailable` (FR-5) ; sinon `entry.label` de l'état courant (FR-3) s'il existe ; sinon `tile.subtitle`. Si elle est non vide, un `<span class="tile-subtitle" title="<texte complet>">` la rend juste après `.tile-label`, comme texte. Sans aucune des trois, aucun `.tile-subtitle` n'est rendu. `.tile-label` (le nom) est inchangé.
- **FR-5**: **Erreur.** Une tuile standalone est en erreur quand son `entity` est absent de `hass.states`, quand son état est `unavailable`, ou quand son état est égal à `tile.state_error`. En erreur, `.hexa-tile` porte `data-error="true"`, ni `data-state-color` ni `--sf-tile-state-color` ; bordure, icône et nom prennent `var(--sf-error)`, et un `<sf-icon class="tile-mark">` d'icône `mdi:alert-octagon-outline` couleur `var(--sf-error)` est rendu — l'erreur ne repose jamais sur la seule couleur. Absente ou `unavailable`, l'`aria-label` est `<nom>, <msg('Unavailable')>` et la seconde ligne est `msg('Unavailable')` (FR-4).
  - **FR-5.1**: Absente ou `unavailable` : un toucher et un double toucher n'émettent rien. Un appui long sur une entité `unavailable` ouvre more-info (FR-8) ; sur une entité absente, il n'émet rien. Une tuile en erreur par `state_error` agit normalement. Cette garde est évaluée au moment de l'émission (FR-9 : toucher différé). Un toucher ou un double toucher ainsi muet affiche le toast `<nom> : <msg('Unavailable')>` (FR-7.8, réponse D3.2 au spike).
- **FR-6**: **Toucher.** Un `click` sur une tuile personnalisée, ainsi qu'un `keydown` `Enter` ou ` ` (espace) sur elle, déclenche le geste « toucher » résolu par FR-2 (sous réserve de FR-5.1, FR-8 et FR-9). Les deux touches reçoivent `preventDefault` ; un `keydown` dont `event.repeat` est vrai est ignoré (aucune émission). Le clavier n'ouvre jamais de fenêtre de double toucher : sur une tuile avec `double_tap_action`, `Enter` émet le toucher aussitôt (agent's call : deux `Enter` ne sont pas un geste attendu, et un retard de 250 ms au clavier ne sert à rien). La carte n'ajoute, ne lit ni n'exige aucune clé `confirmation`, et n'affiche aucun dialogue.
- **FR-7**: **Attente — début.** Quand un geste toggle (toucher, appui long ou double toucher) émet sur une tuile standalone avec `entity`, non bloqué par FR-5.1, la carte entre — ou rentre, si une attente court déjà — en attente pour cette **entité** : elle mémorise l'état courant, efface la marque sans effet et (ré)arme un seul minuteur, de la durée `pending_timeout` de la tuile qui a émis (FR-7.3) ; sur une entité en `opening` / `closing`, le geste émet sans démarrer d'attente (FR-7.5) ; toute tuile de cette entité porte `data-pending="true"`, `aria-busy="true"` et l'`aria-label` `<nom>, <msg('Pending')>`. Aucune autre action (`perform-action`, `navigate`, `more-info`, `call-service`…) ne démarre d'attente.
  - **FR-7.1**: **Aucun blocage pendant l'attente.** Pendant l'attente d'une entité, et tant que son état est `opening` ou `closing` (FR-7.5), tout geste — toggle compris, sur n'importe quelle tuile de l'entité — émet normalement : ouvrir le portail, l'arrêter en route pour laisser passer un piéton ou un vélo, puis le refermer, ce sont trois touchers qui émettent chacun (réponse D2.2 au spike, FR-7.6). Chaque geste toggle relance l'attente (FR-7). Seule FR-5.1 rend un geste muet.
  - **FR-7.2**: À chaque affectation de `hass`, si l'état de l'entité en attente diffère de l'état mémorisé (y compris `unavailable` ou absence), l'attente prend fin sans marque : le minuteur est annulé, `data-pending` et `aria-busy` disparaissent, le rendu suit le nouvel état (FR-3). Si le nouvel état est `opening` ou `closing`, la tuile passe sans interruption à l'état « en mouvement » (FR-7.5). Une attente terminée ne reprend jamais : `closed` → toucher → `opening` → `closed` finit sans marque, sur le rendu de `closed` (agent's call : l'entité a réagi, la commande n'est pas « sans effet »).
  - **FR-7.3**: Si l'état n'a pas changé `pending_timeout` secondes après le début (valeur numérique finie, strictement positive et ≤ 86 400 ; sinon, absente comprise, 30), l'attente prend fin avec la marque « sans effet » sur toutes les tuiles de l'entité, et le toast de FR-7.8 : `data-no-change="true"`, un `<sf-icon class="tile-mark">` d'icône `mdi:alert-circle-outline` couleur `var(--sf-warning)`, `aria-label` `<nom>, <msg('No change')>` ; la couleur, l'icône et la seconde ligne restent celles de l'état inchangé [AE-2]. Ex. : `pending_timeout: 5` → marque à 5 000 ms, pas à 4 999 ms ; `0`, `-1`, `'x'`, `86401`, `1e9` → 30 000 ms ; `86400` → 86 400 000 ms. La marque disparaît au prochain changement d'état de l'entité ou au prochain début d'attente. Une tuile porte au plus un `.tile-mark` : en erreur (FR-5), la marque d'erreur remplace la marque sans effet (agent's call).
  - **FR-7.4**: `disconnectedCallback` annule tous les minuteurs de la carte — attente, appui long, fenêtre de double toucher — efface attentes, marques et l'indicateur de `click` ignoré (FR-8), sans rien émettre.
  - **FR-7.5**: **En mouvement.** Une tuile standalone dont l'entité est dans l'état `opening` ou `closing` porte `data-pending="true"`, `aria-busy="true"` et l'`aria-label` `<nom>, <msg('Pending')>`, sans minuteur ni marque ; ses gestes émettent normalement, sans démarrer d'attente (FR-7, FR-7.1). L'état prend fin dès que l'entité quitte `opening` / `closing`. Le style par état (FR-3) s'applique s'il existe une clé `opening` / `closing`, et la tuile clignote vers le bleu clair comme en attente (FR-10, demande utilisateur du 2026-11-19 : le portail en mouvement ne se voyait pas). Rendu : décision utilisateur du 2026-11-18 ; gestes non bloqués : réponse D2.2 au spike.
  - **FR-7.6**: **Décision utilisateur du 2026-11-18 (spike, D2.2) — pas de blocage.** Pendant l'attente et en mouvement, aucun geste n'est bloqué (FR-7.1), et seule une action `toggle` démarre l'attente (FR-7). Raison : le portail se pilote par impulsions successives (ouvrir, arrêter en route, refermer), et attendre 30 s n'est pas acceptable. Risque assumé : un double appui involontaire envoie deux impulsions (le portail s'ouvre puis s'arrête) ; la carte ne le détecte pas, l'utilisateur retouche. Menace laissée de côté : une commande lancée hors de la carte (autre appareil, automatisation) sur une entité qui ne rapporte pas son mouvement n'est pas détectable par la carte.
  - **FR-7.7**: **Annonce.** La carte rend un seul `<span class="sf-live" role="status" aria-live="polite">`, hors des tuiles. À la fin d'une attente par changement d'état (FR-7.2), son texte devient `<nom>, <seconde ligne du nouvel état, sinon l'état brut>` ; à la marque sans effet (FR-7.3), `<nom>, <msg('No change')>`. Une tuile dont l'état courant correspond à une entrée de `states` (FR-3) a l'`aria-label` `<nom>, <entry.label ?? état brut>` hors attente, marque et erreur.
  - **FR-7.8**: **Toast.** La carte rend un seul `<sf-toast>` (composant existant `src/components/sf-toast.ts`), hors des tuiles, et y pousse ses messages par `addMessage(texte, true)`, textes traduits par `msg()` (réponses D1.2, D2.1 et D3.2 au spike) : à la marque sans effet (FR-7.3), `<nom> : <msg('No change')>` — une fois par échéance, pas une fois par tuile ; à un toucher ou un double toucher muet sur une entité absente ou `unavailable` (FR-5.1), `<nom> : <msg('Unavailable')>`. Aucun autre geste ne pousse de toast. Les minuteurs propres à `sf-toast` (disparition du message) ne relèvent pas de FR-7.4.
- **FR-8**: **Appui long.** Un `pointerdown` du bouton principal sur une tuile personnalisée arme un minuteur de `HOLD_MS` (500 ms). `pointerup`, `pointercancel`, `pointerleave`, ou un `pointermove` à plus de `MOVE_TOLERANCE_PX` (10 px) du point de départ, le désarment. À l'échéance : si `hold_action` est défini avec `action !== 'none'`, `fireHassAction(this, tile, 'hold')` (un toggle relance l'attente, FR-7) ; si `hold_action.action === 'none'`, rien ; sans `hold_action`, more-info de `entity` (`fireHassAction(this, {entity, tap_action: {action: 'more-info'}}, 'tap')`) si la tuile en a une, sinon rien [AE-3]. `contextmenu` est annulé (`preventDefault`) sur les tuiles personnalisées.
  - **FR-8.1**: **Click ignoré.** La carte tient un indicateur « ignorer le prochain `click` », posé quand un appui long se déclenche, sur `pointercancel`, et sur un `pointermove` au-delà de `MOVE_TOLERANCE_PX`. Il est effacé au `pointerdown` suivant et par `disconnectedCallback` (FR-7.4) ; le premier `click` qui le trouve posé l'efface et n'émet rien. Le clavier (FR-6) ne le lit jamais. Un geste qui commence par `pointerdown` ne peut donc jamais être avalé par un indicateur périmé.
- **FR-9**: **Double toucher.** Seulement si `double_tap_action` est défini avec `action !== 'none'` : un premier `click` arme, **pour cette tuile**, une fenêtre de `DOUBLE_TAP_MS` (250 ms) ; un second `click` sur la même tuile dans la fenêtre émet `fireHassAction(this, tile, 'double_tap')` et aucun toucher ; sinon le toucher part à la fin de la fenêtre, après réévaluation de FR-5.1. Un `click` sur une autre tuile n'interagit pas avec cette fenêtre. Sans `double_tap_action` actif, le toucher part au `click`, sans délai.
- **FR-10**: **Styles** (`src/cards/hexa-tiles/styles.ts`) : `[data-state-color="true"]` colore `.hexa-border` (stroke, drop-shadow), l'icône (`--icon-color`) et `.tile-label` / `.tile-subtitle` avec `var(--sf-tile-state-color)` ; `[data-error="true"]` fait de même avec `var(--sf-error)` ; pendant l'attente et en mouvement (`[data-pending="true"]`, FR-7, FR-7.5), la tuile **clignote entre la couleur de son état courant et le bleu clair `var(--sf-primary)`** (demande utilisateur du 2026-11-19 au workbench : la pulsation d'opacité 1 → 0,3 ne se voyait pas sur un téléphone ; lecture retenue : bleu clair = `--sf-primary`, `var(--primary-color, #00d2ff)` dans `src/styles/common.ts`, le thème n'ayant pas de jeton bleu clair plus précis) — `.hexa-border` est animée par `@keyframes sf-hexa-pending` (`stroke` vers `var(--sf-primary)`, trait épaissi et halo bleu clair ; `1s`, alternée, infinie : un aller-retour toutes les deux secondes, le rythme de la pulsation d'avant le lot — le 2026-11-19 l'utilisateur a jugé `0.5s` trop rapide au workbench ; l'opacité n'est pas animée) et l'icône d'état (`.hexa-content sf-icon:not(.tile-mark)`) par `@keyframes sf-hexa-pending-icon` (`--icon-color` à `var(--sf-primary)` au milieu du cycle, `2s`, infinie) ; une `.tile-mark` (erreur FR-5, sans effet FR-7.3) n'est jamais animée et garde sa couleur ; sous `@media (prefers-reduced-motion: reduce)`, ni la bordure ni l'icône ne sont animées (`animation: none`) et `.hexa-border` porte un trait bleu clair fixe en pointillés (`stroke: var(--sf-primary)`, `stroke-dasharray`) ; `.tile-subtitle` tient sur une ligne avec ellipse ; `.tile-mark` est positionnée en haut du contenu ; `.sf-live` est masquée visuellement mais lue par les lecteurs d'écran (`position: absolute`, `width: 1px`, `height: 1px`, `overflow: hidden`, `clip-path: inset(50%)`) ; `.hexa-tile` porte `user-select: none` et `-webkit-touch-callout: none`.
- **FR-11**: **Éditeur — section Actions.** Chaque tuile de l'éditeur gagne une section accordéon `msg('Actions')` après la section technique, contenant : `sf-editor-input` `element-id="subtitle"` (`msg('Subtitle')`), `sf-editor-input` `element-id="pending_timeout"` `type="number"` (`msg('Pending timeout (s)')`), et trois `sf-editor-action` `element-id` `tap_action` / `hold_action` / `double_tap_action` (`msg('Tap action')`, `msg('Hold action')`, `msg('Double tap action')`). Sous le champ `double_tap_action`, un `<p class="hint">` affiche `msg('A double tap action delays every tap by 250 ms')`. Une valeur vide ou nulle **supprime** la clé de la tuile ; `pending_timeout` est écrit comme nombre (`'20'` → `20`), une saisie non numérique supprime la clé.
- **FR-12**: **Éditeur — styles par état.** La section Actions liste chaque entrée de `tile.states` dans l'ordre : `sf-editor-input` clé d'état (`msg('State')`), `sf-editor-color-picker` (`msg('Color')`), `sf-editor-dropdown-icon` (`msg('Icon')`), `sf-editor-input` libellé (`msg('Label')`), et un `sf-button` de suppression (`msg('Remove')`) ; un bouton `msg('Add state')` ajoute une entrée vide sous la première clé libre parmi `on`, `off`, `open`, `closed`, sinon `state_<n>` (plus petit `n ≥ 1` libre). Renommer une clé conserve l'entrée et sa position ; le renommage est validé à la sortie du champ (`focusout`) ou à `Entrée`, jamais à chaque frappe (une clé à moitié tapée n'est jamais écrite) ; renommer vers une clé existante ou vide ne change pas la config et remet le champ affiché (l'`<input>` interne de `sf-editor-input`) à l'ancienne clé. Un champ vidé supprime sa sous-clé ; la dernière entrée supprimée retire `states`. Quand l'entité de la tuile est dans `hass.states`, un `<p class="hint">` au-dessus de la liste affiche `msg('Current state')` suivi de l'état brut (ex. `closed`), pour rappeler que la clé doit lui être strictement égale, casse comprise (FR-3). Les clés sont des chaînes JS ; leur sérialisation YAML (guillemets autour de `on` / `off`) revient à HA, et la page wiki (FR-15) cite les clés entre guillemets. Décision utilisateur du 2026-11-18 : l'éditeur garde ce niveau, avec ces retours.
- **FR-13**: **i18n.** Chaînes source nouvelles et leur traduction fr dans `xliff/fr.xlf` et `src/locales/locales/fr.js` régénéré (`npm run localize-extract`, `npm run localize-build`) : `Pending` (`En cours`), `No change` (`Sans effet`), `Subtitle` (`Sous-titre`), `Pending timeout (s)` (`Délai d'attente (s)`), `Tap action` (`Action au toucher`), `Hold action` (`Action à l'appui long`), `Double tap action` (`Action au double toucher`), `Color` (`Couleur`), `Label` (`Libellé`), `Add state` (`Ajouter un état`), `Current state` (`État actuel`), `A double tap action delays every tap by 250 ms` (`Une action au double toucher retarde chaque toucher de 250 ms`). `Unavailable`, `State`, `Icon`, `Actions`, `Remove` existent déjà (SHOW — `grep -c "<source>Unavailable</source>" xliff/fr.xlf` → 1, idem pour les quatre autres ; les douze nouvelles → 0, relu le 2026-11-18 pour `Current state` et la phrase du double toucher).

## Anti-patterns

| # | Anti-pattern | Instead |
|---|--------------|---------|
| 1 | Ajouter une étape de confirmation (clé `confirmation`, dialogue de la carte ou natif) sur une tuile | toucher = action immédiate, FR-6 (veto utilisateur 2026-11-18) |
| 2 | Terminer l'attente sur une animation de durée fixe, ou afficher la couleur de l'état cible avant que HA ne le rapporte | fin sur changement d'état ou échéance avec marque, FR-7.2 / FR-7.3 |
| 3 | Bloquer les gestes pendant l'attente ou en mouvement (l'utilisateur doit pouvoir arrêter le portail en route) | chaque geste émet et un toggle relance l'attente, FR-7.1 |
| 4 | Coder le toggle par domaine dans la carte (`callService('cover', 'open_cover', …)`) | `hass-action` + frontend HA, FR-6 |
| 5 | Concaténer la couleur utilisateur dans l'attribut `style` | `styleMap` / custom property, FR-3 |
| 6 | Retarder chaque toucher de 250 ms pour détecter un double toucher non configuré | délai seulement si `double_tap_action` actif, FR-9 |
| 7 | Utiliser la même couleur rouge `--sf-error` pour la marque « sans effet » qu'un état « ouvert » configuré en rouge | marque distincte `--sf-warning` + icône, FR-7.3 |
| 8 | Un indicateur « ignorer le prochain click » sans règle d'effacement | effacé au `pointerdown` suivant, consommé par le premier `click`, FR-8.1 |
| 9 | Passer une durée utilisateur non bornée à `setTimeout` (au-delà de 2³¹-1 ms il part aussitôt) | borne 86 400 s, sinon 30, FR-7.3 |
| 10 | Signaler une erreur par la seule couleur | marque `.tile-mark` + seconde ligne `Unavailable`, FR-5 |

## Error Handling

| Error | Detection | Response | Fallback |
|-------|-----------|----------|----------|
| entité de tuile absente de `hass.states` (faute de frappe, entité supprimée) | `hass.states[entity] === undefined` | style erreur, marque, seconde ligne et `aria-label` `… Unavailable`, aucun geste n'émet, toast au toucher (FR-5, FR-5.1, FR-7.8) | nom = `tile.name ?? entity` |
| entité `unavailable` (relais Zigbee hors ligne, `availability` du template faux) | `state === 'unavailable'` | style erreur et marque ; toucher / double toucher muets avec toast ; appui long → more-info (FR-5.1, FR-7.8) | — |
| état égal à `state_error` | `state === tile.state_error` | style erreur et marque, gestes normaux (FR-5) | — |
| impulsion de relais perdue ou service HA en échec (le frontend affiche son propre toast) | état inchangé à l'échéance `pending_timeout` | fin d'attente, marque « sans effet » `--sf-warning`, couleur de l'état réel, annonce et toast (FR-7.3, FR-7.7, FR-7.8) | nouveau toucher relance |
| `pending_timeout` absent, nul, négatif, non numérique, ou > 86 400 | `!(Number.isFinite(v) && v > 0 && v <= 86400)` | 30 s (FR-7.3) | — |
| entité en mouvement (`opening` / `closing`) | `state === 'opening' \|\| state === 'closing'` | rendu en attente, gestes émis, sans minuteur (FR-7.5) | — |
| `states` ou une de ses entrées mal formés (`null`, chaîne, tableau, champ non chaîne) | pas un objet simple / pas une chaîne non vide | ignoré comme absent, aucun `throw` (FR-3.1) | rendu d'avant le lot |
| couleur `states.*.color` invalide en YAML | CSS invalide au calcul | la propriété personnalisée invalide rend la bordure sans stroke — non détecté par la carte ; l'éditeur ne produit que des hex valides (color picker) | corriger le YAML |
| `hass-action` non traité (workbench sans frontend HA) | aucun changement d'état | attente puis marque sans effet (FR-7.3) | — |
| geste interrompu par un défilement sur téléphone | `pointermove` > 10 px ou `pointercancel` | aucun appui long (FR-8) ; le `click` éventuel qui suit est ignoré (FR-8.1) | — |

## Non-Goals

- aucune étape de confirmation, sur aucune tuile (veto utilisateur 2026-11-18) ;
- aucun curseur de luminosité ou de position, aucune planification, aucun helper HA créé par la carte ;
- tuile météo, en-tête et tuiles agrégées (`entity_kind`) : pas de `states`, pas d'attente ;
- lecture d'une seconde entité par tuile (ex. `binary_sensor.mureva_evlink_charge`) : une tuile lit une entité — le switch de la borne est actif pendant la charge et inactif quand elle est terminée (réponse D4.1 au spike) ;
- radiateur : retiré du lot (réponse au spike du 2026-11-18) ; la télé n'est qu'une tuile toggle allumer / éteindre, sans travail propre.
